# ORX Analytics 菜单栏应用设计（首版）

- 状态：已接受。用户 2026-10-16 交付本设计稿，ORX 控制器同日逐项核对通过（事实锚点与两仓现状一致）。
- 执行：本仓 ORX Goal G002，五阶段推进（见根目录 `IMPLEMENTATION_PLAN.md`，完成后移除）。
- 定位：沿用 ADR-0001 独立仓库定位——菜单栏应用放在 orx-analytics 中，复用现有分析核心；ORX 主项目只增加必要的发现契约（用户级项目索引）。

**产品定义：ORX Analytics 是常驻 macOS 菜单栏的本地任务观察工具，帮助你先发现正在执行和需要关注的任务，再查清每次执行的 token 消耗、重试和验证开销。**

---

## 1．产品目标与首版边界

主要使用路径：

> 看正在进行和异常的执行 → 点开具体任务 → 查看消耗及原因 → 必要时查询历史。

首版需要回答五个问题：

| 问题 | 产品提供的答案 |
|---|---|
| 现在有哪些 ORX 执行？ | 跨项目的进行中执行列表 |
| 哪些需要我关注？ | 当前失败、阻塞、明确异常及其依据 |
| 一个任务消耗了多少？ | 所有可归属尝试的 token、来源和覆盖情况 |
| 为什么消耗较多？ | worker、重试、verifier、规划开销的分解 |
| 以前的任务在哪里？ | 按项目、目标、任务、状态查询历史 |

“所有任务”的首版定义：**本机已登记项目，以及启用发现机制后由 ORX 自动登记的项目中，仍可读取的执行历史。** 不承诺自动找回已经删除的数据，也不把远程机器、其他用户账户和未发现目录中的任务隐含算入覆盖范围。

首版包括状态观察、历史查询、消耗分析和安装常驻。任务启动、停止、重试、修改计划等控制操作留在 ORX 中。

## 2．任务模型：界面简单，身份必须完整

沿用 ORX 的真实层级：

```text
Project 项目
  └─ Goal 目标
       └─ Run 一次执行
            └─ Revision 一版计划
                 └─ Task 子任务
                      └─ Attempt 一次执行尝试
```

界面不必让用户逐层点击：

- 菜单栏以 **Run 执行卡片** 为主，显示项目、目标名称和当前子任务。
- 执行详情直接列出 Tasks。
- 点击 Task 查看 Attempts、验证和用量。
- Revision 默认收起，需要调查重规划时再展开。

身份规则：

| 对象 | 身份 |
|---|---|
| Project | 解析符号链接后的项目绝对路径，沿用现有 registry |
| Run | Project + run_id |
| Task | Project + Run + Revision + task_id |
| Attempt | Project + 源数据库中的 attempt_id |

`T001`、`R001` 都不能作为跨项目唯一键。不同计划版本中的同名任务也不能直接合并。

项目移动后，首版通过“重新定位项目”显式关联历史；不能仅凭目录名相同自动认定为同一个项目。

## 3．菜单栏与详情窗口

采用 **菜单栏快速面板 + 独立详情窗口**。

菜单栏显示：

```text
[ORX 图标] 3
```

数字固定代表“进行中的 Run 数量”，不能在任务数、会话数和执行数之间切换。需要关注时增加可辨识标记，并提供文字说明，不能只依靠颜色。不默认把持续变化的 token 数字放在系统菜单栏中。

快速面板结构：

```text
ORX Analytics                    刷新状态

进行中 3     需要关注 1

需要关注
  项目 / 目标
  当前问题与发生时间
  当前任务 / 已观测消耗

进行中
  项目 / 目标
  当前执行阶段、子任务进度
  已观测消耗、数据完整程度

最近完成
  最近几次执行

查看全部执行…       设置…       退出
```

规则：

- 同一 Run 只出现一次，异常优先排序。
- 显示“已完成任务数 / 当前计划任务数”，不要伪装成精确的工作量百分比。
- 当前计划的进度与历史计划消耗分开表达。
- 最近完成只保留少量入口，完整历史进入详情窗口。
- 打开面板先展示缓存，再异步刷新，不能等待采集完成才显示。
- 点击卡片打开对应执行详情，保留项目和执行上下文。

详情窗口四组内容：

| 区域 | 内容 |
|---|---|
| 执行概况 | 项目、目标、Run、状态、开始时间、经过时长、数据更新时间 |
| 任务列表 | 当前计划任务、状态、执行次数、已观测 token、异常提示 |
| 消耗分析 | worker / verifier / planner 分解，模型分布，缺失说明 |
| 尝试与证据 | 每次 Attempt 的结果、用量、会话关联、失败原因和来源 |

历史查询支持项目、目标或任务标题、Run/Task 编号、状态、模型、时间范围；支持按时间和已观测消耗排序。消耗排序必须同时展示覆盖程度，不能让缺数据的任务看起来特别“省”。

交互采用系统外观、键盘导航和明确的状态文字。关闭窗口后继续驻留，只有“退出”才结束应用驻留。

## 4．状态设计：执行状态、异常和数据健康分开

不要用一个红黄绿状态同时表达所有事情。每个 Run 至少有三组独立信息：

| 维度 | 示例 |
|---|---|
| 执行状态 | 规划中、执行中、等待验证、暂停、完成、失败 |
| 关注事项 | 当前阻塞、重复失败、疑似停摆、用量异常 |
| 数据健康 | 正常、更新延迟、来源不可读、版本不支持 |

执行状态必须从 ORX 的事实映射而来，保留原始状态值；新增或不认识的值显示“未知状态”，不能猜成完成或失败。

“需要关注”按当前事实判断：

- 一次历史 Attempt 失败，但新 Attempt 已接替运行，显示“重试中”。
- 历史失败已经恢复，不继续占据当前异常列表。
- 等待前置任务本身不是异常。
- 没有 heartbeat 只能表示“未提供进度报告”，不能判定已经卡死。
- “最后采集时间”和“最后任务进展时间”分别显示。

异常必须能点开看到触发依据、时间、置信度和恢复情况。

通知默认关闭，用户开启后再申请系统权限。相同异常去重；同一轮多个异常合并通知；低置信度推测默认只在面板中显示。通知点击进入对应执行。

## 5．token 口径：最重要的数据契约

主指标命名为 **“已观测 token”**，避免把不完整观测误写成最终消耗。

三类数字必须区分：

| 类型 | 含义 | 展示方式 |
|---|---|---|
| ORX 已记录用量 | ORX 中规范观测对应的统计 | 主要统计，附覆盖率 |
| 原生会话预览 | 来源支持时，读取运行中会话的当前累计量 | 独立展示，标注来源与更新时间 |
| 费用 | 有明确计费依据后的金额 | 首版不提供 |

ORX 已记录用量和会话预览可能描述同一批 token，**不能相加**。首版保留两条口径，不制造混合总数。部分用量要等 Attempt 结束后才补录，因此执行中的数字不承诺持续实时增长。

任务归属规则：

- Task 消耗包含其所有可明确归属的 worker Attempts，包括失败和重试。
- 能明确关联到该 Task 的 verifier 消耗计入任务，并单列。
- planner 保留在 Run 的规划开销中。
- controller 自身消耗单列；只有归属证据充分时才计入该 Run。
- 无法归属的消耗列入“未归属”，不按任务数量或时间比例摊分。
- 父会话和子会话不能重复计数；重叠会话子树必须检查归属冲突。

Run 汇总覆盖该 Run 的所有计划版本，不能因为重规划就丢掉旧版本消耗：

```text
Run 已归属消耗
  = 各版本 Task 可归属消耗
  + planner 等可明确归属的执行开销
```

controller、未归属会话等独立账目应同时展示，不能悄悄塞入其中。

底层继续遵守现有规范观测优先级：

```text
native_cli > zcode_db > host_report > output_estimate
```

不同来源不是可以累加的多份消耗。

输入、输出、缓存保留来源原始语义。若新增“标准化处理量”，必须作为**单独、有版本的派生指标**：

- 已知缓存包含于 input：`input + output`。
- 已知缓存与 input 分离：`input + cached + output`。
- 缓存语义或必要字段未知：结果保持未知或明确的部分和。
- 不把 reasoning 等可能属于 output 子集的字段重复相加。

现有 [指标冻结契约](metrics.md) 不应被界面需求静默改写。新增派生口径需要补充契约与回归测试。

每个汇总都应携带：

- 已观测 Attempts / 应统计 Attempts。
- 字段缺失数量。
- exact / estimated / unknown 分布。
- 来源和数据截至时间。

例如：已观测 128K token；8/10 次尝试有用量，包含估算。

完全未知显示 `—`。只有来源明确记录为零才能显示 `0`。

首版不做“准确今日消耗”：跨天执行和结束后补录，会让“今天入库”与“今天实际发生”不一致。后续需要按时间可归属的请求明细或累计差量建立独立口径。

## 6．自动发现：ORX 提供索引，analytics 消费事实

推荐增加 **ORX 用户级项目索引**：

- 由 ORX 维护，位置通过 ORX 配置规则解析。
- ORX 创建或启动执行时，登记项目 canonical path、索引版本、最后见到时间。
- 索引只用于发现项目，状态和用量仍以项目 `.orx/state.db` 为准。
- analytics 只读消费索引。
- ORX 不需要导入 analytics，也不等待其进程响应。
- 索引更新失败不得阻止执行，但应记录可诊断的信息。
- 并发更新需要锁和原子写入，不能覆盖其他项目记录。

首次使用同时支持：

1. 导入现有 analytics 已登记项目。
2. 用户选择若干工作目录，进行有界扫描，补齐旧项目。
3. 手动添加项目目录。

扫描需要深度限制，跳过依赖目录、Git 内部目录及符号链接循环；不做全磁盘扫描。

旧版 ORX 不提供索引时，仍支持已登记项目，但明确提示“自动发现范围受限”。项目删除或暂时不可访问时保留历史缓存，标记来源不可用。

## 7．技术架构与仓库职责

推荐 **SwiftUI 原生外壳 + 复用 Python 分析核心**。SwiftUI 的 `MenuBarExtra` 提供常驻入口和窗口式面板；应用通过 `LSUIElement` 采用菜单栏应用形态。

```text
ORX 项目索引 / 各项目 state.db / 支持的原生会话
                     ↓ 只读
             Python 采集与分析核心
                     ↓
          analytics 自有数据库与查询模型
                     ↓ 本地 IPC
       SwiftUI 菜单栏 / 详情窗口 / 设置
```

模块分工：

| 模块 | 职责 |
|---|---|
| Discovery | 合并索引、手动登记和扫描结果 |
| Collection | 只读采集、增量处理、来源能力检测 |
| Read Model | 跨项目列表、任务详情、归属和指标计算 |
| Engine | 调度、采集互斥、查询、健康状态 |
| macOS App | 展示、导航、通知、登录启动 |

Swift 层不直接写业务 SQL，也不再实现一套 token 算法。

在本仓增加 `apps/macos/` 等应用目录；Python 包保留原有 CLI 能力。ORX 仓库只承担项目索引及其契约测试。

查询接口至少具备：

| 接口 | 用途 |
|---|---|
| `overview` | 活动执行、关注事项、来源健康 |
| `runs.list` / `runs.get` | 历史查询与执行详情 |
| `tasks.get` | 任务和 Attempts 明细 |
| `projects.list` | 登记和可访问情况 |
| `health` | 引擎、来源、协议版本 |
| `refresh.request` | 请求刷新并返回作业标识 |

所有查询返回协议版本、生成时间、项目快照标识、覆盖情况和警告。列表分页，排序带稳定身份作为次级键。一个项目的关联查询必须使用同一成功快照；跨项目结果分别保留更新时间。

**进程与 CLI 协作**

每个 data-dir 只有一个协调引擎，通过用户私有 Unix socket 提供本地 JSON 协议，不开 HTTP 端口。

- App 与新版 CLI watch 都连接同一引擎。
- 引擎用系统文件锁保证唯一实例，不能仅依赖 PID 文件。
- App 可启动引擎；CLI watch 可以独立持有持续采集需求。
- 退出 App 释放自己的需求，不停止 CLI 已要求继续运行的采集。
- 协议不兼容时报告版本问题，不强行接管。
- 检测旧版独立 watcher，提供明确迁移流程，不按 PID 盲目终止进程。

现有 `src/orxanalytics/watch.py` 需要完成这层协调改造，不能直接由 App 无条件执行 `watch start/stop`。

## 8．刷新、容错与本地数据

初始调度参数（后续依据实测调整）：

| 场景 | 目标刷新间隔 |
|---|---|
| 面板或详情打开 | 活动项目状态约 5 秒 |
| 后台存在活动执行 | 约 15 秒 |
| 全部空闲 | 约 60 秒 |
| 历史项目完整核对 | 低频执行，或手动触发 |

这些是状态检查目标，不能被解释为 token 每 5 秒就有新数据。

采集策略：

- 状态刷新、用量导入、异常分析分别调度。
- 多个刷新请求合并，单来源任务不能无限排队。
- 不因每次界面刷新就追加完整 ORX 快照。
- 使用变化检测降低开销，并定期完整核对，不能只凭文件时间判断永远不变。
- 一个项目失败不影响其他项目。
- 失败时保留最后成功数据，附失败原因及旧数据时间。
- 睡眠期间不判断任务停摆；唤醒后重新同步。
- 引擎崩溃后有限重启并退避，重复失败显示诊断入口。

继续使用现有 analytics data-dir 与 registry，避免 CLI 和 App 各自保存一份数据。App 默认使用现有默认目录；自定义目录可以在设置中显式选择。

源库读取必须遵循 ORX 只读契约（见 ORX 仓 `docs/observability-contract.md`）：版本白名单、命名列查询、WAL 感知、只读连接，不调用可能触发迁移的 ORX Store 或命令。

本地日志有容量限制，不默认记录完整提示词、密钥或会话正文。诊断包导出前展示内容范围。

## 9．安装与常驻交付

最终交付必须是 **可安装的 `ORX Analytics.app`**。Python CLI 安装成功不能算菜单栏功能交付。

首版：

- 最低 macOS 13，先交付 Apple Silicon 构建。
- App 内置固定版本 Python 运行时和分析代码。
- 无需预装 Python、uv 或 Homebrew。
- 发布 DMG 或包含 `.app` 的归档。
- 复制到 Applications 后双击即可出现菜单栏图标。
- 首次启动展示已发现项目、数据健康和添加入口。
- 登录启动作为可选设置，默认关闭。
- 通过 `SMAppService.mainApp` 管理登录启动，并显示系统实际状态。

对外分发目标包含签名与公证；本机开发构建应与正式分发包明确区分。

首版允许手动下载升级，不必先引入自动更新框架。升级要保护 analytics 自有数据库，先备份再迁移；回退到不兼容旧版时明确拒绝读取，不能损坏数据。

退出或卸载 App 不删除 ORX 项目数据。清理 analytics 缓存必须是单独、明确的操作。

## 10．五阶段计划

| 阶段 | 交付内容 | 验收重点 |
|---|---|---|
| 1．冻结契约与查询模型 | 状态映射、身份、token 口径、跨项目查询及测试夹具 | 跨项目/版本同编号不串账；缺失不补零；重试与验证归属正确 |
| 2．发现与协调引擎 | ORX 项目索引、analytics 发现、单引擎与调度 | 并发登记不丢项目；App/CLI 共存；未知 schema 隔离；源库无写操作 |
| 3．原生菜单栏闭环 | 常驻入口、快速面板、执行/任务详情 | 从进行中执行进入任务消耗；刷新不阻塞界面；关闭窗口仍驻留 |
| 4．历史与运行完善 | 搜索、通知、设置、睡眠恢复、错误与诊断 | 异常去重；恢复不反复报警；旧数据明确标注；单源失败不拖垮整体 |
| 5．安装与发布验证 | 内置运行时、应用包、安装与升级文档 | 干净 Mac 无开发环境可启动；登录启动有效；升级保留数据 |

执行时按仓库规范创建 `IMPLEMENTATION_PLAN.md`，逐阶段更新，全部完成后移除。不要跳过前两阶段，先做出漂亮但数字不可信的面板。

测试至少覆盖：

- 重复采集、刷新、重启不重复计数。
- 同 Task 多次重试、多个 verifier、跨 Revision 重做。
- planner 无 Revision 仍归属正确。
- 原生会话预览与 ORX 记录不重复相加。
- 缓存包含、缓存分离、字段缺失和归属不明确。
- 一个会话对应多个 Attempts，或会话子树发生重叠。
- ORX 正在写入 WAL 时仍能读取已提交状态。
- 项目不可读、旧版/新版 schema、损坏来源、引擎崩溃。
- App 与 CLI watcher 并存、退出与升级。
- 从实际安装包启动，而非仅从 Xcode 启动。

性能先设为验收目标：在约 20 个项目、1 万条任务记录的基准数据下，缓存面板打开 P95 小于 300ms，历史分页查询 P95 小于 1 秒；无采集工作时不持续占用 CPU。达标情况必须实测记录。

## 11．最终完成标准

交付时应能实际演示：
