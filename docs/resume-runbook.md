# 停摆恢复操作卡（任意 ZCode 编排会话，含非 ORX 项目）

依据：R006 controller 停摆 2.48h（GLM 配额快速失败）、To2050
2026-10-06 controller 停摆 2h47m（03:17 错误 turn 后无人接续到 05:44）、
同日 09:12 一分钟恢复（LE11 续做）。三次同款签名：
**status=error、1 个模型请求、0 retry、0 token、0 工具调用**——
单请求快速失败，会话静默死亡，直到有人碰巧回来。

## 信号怎么来

- `fast_fail_stall` 规则：会话**最新 turn** 是零 token 错误 turn 即报
  （confidence=signal），watch 下一轮（默认 ≤10min）触发并发 mac 通知。
- `no_progress` 是兜底：要 gap≥1h 才够得着，报出时停摆已发生至少一小时。
- 注意边界：通知压缩的是**检测延迟**；**响应延迟**仍取决于人。
  操作者在场 → 分钟级（09:12 实证）；操作者在睡觉 → 醒来时的第一条
  通知就是起点，不再依赖碰巧回来看。

## 恢复四步（源自 09:12 实战）

1. **看原会话最后一 turn**：确认是零 token 错误 turn（快速失败），
   不是干活干到一半出错（有 token/工具调用的 error turn 是另一种
   失败，先查做了什么再决定）。
2. **不重试原会话的大动作**：先查工单/任务清单当前归属，确认没有
   并发副作用在路上。
3. **发起续做**：子代理型会话（如 To2050 工单、ORX worker）开新
   attempt/续做单；controller 型会话在新 turn 重述接续点。带上原
   工单号与 attempt 上下文（ORX 侧等价物：G006 的显式 fail/retry、
   `orx task recovery` 显示、迟交拒收——自动接续**明确不做**：
   无法注入 prompt，且无人值守盲续做有副作用重复风险）。
4. **首条消息最小化**：只给接续点与已完成边界，不重放全量上下文。

## 恢复代价 ∝ 发现延迟（量化）

| 案例 | 发现延迟 | 续做代价 |
|---|---|---|
| LE06 续做 | 2h47m（03:17→05:44） | 28.4M token / 162 工具调用 = 首跑 7.1M/44 的 **4.0×** |
| LE11 续做 | ~1min（09:12→09:13） | 6.8M |

结论：早发现，续做成本接近增量；晚发现，上下文重建本身成为大头。

## 顺带：头部任务上下文瘦身的正确杠杆

成本 ≈ 上下文长度 × 请求数（98%+ 是缓存重读）。对 200K 贴顶、
几十 M 级的大任务（To2050 LE13 55.1M / LE12 43.4M）：

- **preread 清单是最弱杠杆**——只瘦前几个 turn，动不了累积转录
  重读的主体。
- **计划性拆分 + 交接工件**才是强杠杆：把大任务在还有小上下文时
  主动拆出"已完成边界 + 剩余范围 + 关键文件清单"的交接工件，
  新会话带工件起跑。与上表同构：有准备的接续 ≪ 无准备的续做。
- controller 只裁决不亲自动手：重读/汇总类活交给子代理，摘要回来。
