# orx-analytics 保持独立仓库和独立工具

orx-analytics 已承担跨项目、跨 agent、包含非 ORX 原生会话的执行观测；
ORX 承担 Goal 的执行控制。决定保持独立仓库、独立 Python 包、独立 CLI
和独立数据目录，通过 ORX 所有的只读契约协作，不并入 ORX 主包，
也不作为 ORX 的 Git submodule。这样可以独立分析原生会话，并让分析工具
的发布和故障与 Goal 执行保持分离。

仓库地址为 `https://github.com/aderan/orx-analytics`。本地 checkout 可位于
任意目录；`Tools` 或 `Products` 只是操作者的目录组织，不成为运行时假设。

## 考虑过的方案

| 方案 | 收益 | 代价与决定 |
|---|---|---|
| 并入 ORX 主包 | 安装一次；可原子修改执行与分析代码 | 原生会话分析也要安装执行控制工具，两类发布节奏耦合；不采用 |
| 独立仓库作为 submodule | ORX 能固定分析工具的源码提交 | 增加指针更新和 checkout 成本，不能保证已安装版本与数据格式兼容；不采用 |
| 独立仓库、契约集成 | 独立安装、独立发布、独立使用 | 需维护版本兼容和跨仓检查；采用 |
| 同一仓库内两个独立包 | 联动修改可以原子提交，同时保留两个安装入口 | 若跨仓联动持续成为主要维护成本，可以重新评估；当前不采用 |

submodule 固定的是源码提交，数据兼容取决于读取契约、指标语义和安装的
工具版本。只有未来明确需要发布固定组合的工具套件源码时，才重新考虑它。

## 后果

- ORX 保存 attempt、session_ref、用量观测、状态、证据和验证等执行事实；
  analytics 保存来源索引、采集游标、快照、关联判断、指标和 findings。
- ORX 的 `docs/observability-contract.md` 是读取 ORX 数据的权威。
  analytics 不导入 `orx.Store`，不迁移源库；自己的 analytics.db 可以独立迁移。
- 软件版本、ORX schema 版本、analytics store 版本是三个不同的版本。
  兼容性检查必须读取数据版本，并验证字段和语义，不能只匹配软件版本号。
- analytics 未安装、未配置或读取失败时，ORX Goal 执行仍能继续。
  ORX 通过显式 `ORX_ANALYTICS_BIN` 可选接入，不猜测本机目录。
- watch 面向多个项目，由操作者管理共享实例。一个 Goal 不接管另一个
  Goal 或操作者启动的 watcher。
- findings 是调查信号，可形成本地 Issue 草案或证据包；不直接修改 ORX
  状态，也不自动发布、恢复执行或修复代码。
- 数据格式或指标语义发生联动变化时，应协调两仓变更并验证读取、报告和
  包内复算。发布前运行兼容性回归和干净环境安装检查。

如果实际使用逐渐只剩 ORX，或多数交付都需要同步修改两仓，应重新比较
同仓独立包的成本。重新组织仓库时仍保留只读契约和独立数据生命周期。
